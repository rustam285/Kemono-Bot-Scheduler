# Техническое задание: VK Post Scheduler

> Веб-приложение для автоматизации создания отложенных постов в VK-группе

---

## 1. Общее описание проекта

Веб-приложение позволяет пользователю:

- Вводить ссылки на посты с внешних платформ (YouTube, Reddit, Twitter/X, Bilibili и др.) и/или загружать локальные файлы
- Автоматически извлекать медиаконтент из этих источников
- Группировать медиа в посты определённого типа (`art`, `fursuit`, `video`)
- Планировать публикацию по временным слотам, начиная с выбранной даты
- Редактировать посты перед публикацией
- Публиковать отложенные посты через VK API
- Управлять уже запланированными постами через календарный интерфейс
- Хранить историю использованных ссылок для предотвращения дублей

---

## 2. Технический стек

> **Примечание по стеку:** Python отдан предпочтение перед Go, поскольку ключевая зависимость `yt-dlp` (загрузка медиа с 1000+ платформ) является нативной Python-библиотекой. Go будет избыточным усложнением без ощутимых преимуществ для данного проекта.

> **⚠️ Важно:** `yt-dlp` и `gallery-dl` обновляются часто, так как платформы регулярно ломают экстракторы. При старте приложения необходимо автоматически выполнять `pip install --upgrade yt-dlp gallery-dl`, иначе экстракторы могут перестать работать в течение недели после последнего обновления (см. §13 — стартовый скрипт).

| Компонент        | Технология                                           |
|------------------|------------------------------------------------------|
| Backend          | Python 3.11+, FastAPI                                |
| Загрузка медиа   | yt-dlp, gallery-dl, httpx                            |
| ffmpeg           | `static-ffmpeg` (Python-пакет, скачивает бинарники автоматически) |
| Frontend         | React 18 + TypeScript, Vite, Tailwind CSS            |
| HTTP-клиент (FE) | TanStack Query (React Query), Axios                  |
| Роутинг (FE)     | React Router v6                                      |
| База данных      | Supabase (PostgreSQL, бесплатный план)               |
| Запуск           | npm-скрипты (`concurrently`) + Python `uvicorn`      |

## 3. Конфигурация

### 3.1 Файл `.env` — только инфраструктурные параметры

`.env` хранит **только** то, что нельзя или не нужно менять из UI: учётные данные Supabase и bootstrap-значения VK для первого запуска. Все операционные настройки (токен VK, таймзона, слоты, задержки и т.д.) хранятся в `settings.json` и управляются через страницу настроек в интерфейсе.

```env
# Supabase (только здесь, не выносить в UI)
SUPABASE_URL=<URL проекта Supabase>
SUPABASE_SERVICE_KEY=<service_role key>   # используется бэкендом для обхода RLS

# Bootstrap VK — используется ТОЛЬКО если settings.json ещё не существует.
# После первого сохранения настроек в UI эти значения игнорируются.
VK_TOKEN=
VK_GROUP_ID=
VK_OWNER_ID=

# Технические параметры
VK_API_VERSION=5.199
LOG_LEVEL=INFO                     # DEBUG | INFO | WARNING | ERROR
MAX_TEMP_SIZE_GB=3                 # макс. суммарный размер /tmp/vk_scheduler
MAX_CONCURRENT_TASKS=3             # макс. одновременных фоновых задач публикации
```

### 3.2 Файл `settings.json` — пользовательские настройки

Хранится на бэкенде в `./data/settings.json` (относительно `backend/`, создаётся автоматически при первом запуске). Создаётся автоматически при первом запуске из bootstrap-значений `.env` или дефолтов. Редактируется через страницу `/settings` в UI.

```json
{
  "vk_token": "...",
  "vk_group_id": 123456,
  "vk_owner_id": 654321,
  "time_slots": ["10:00", "15:00", "20:00"],
  "timezone": "Europe/Moscow",
  "max_download_workers": 3,
  "vk_publish_delay_seconds": 5,
  "ytdlp_timeout_seconds": 30,
  "max_photo_size_mb": 50,
  "max_video_size_mb": 500,
  "cookies_uploaded_at": null
}
```

> **Порядок приоритетов при старте backend'а:**  
> `settings.json` → bootstrap из `.env` → встроенные дефолты.  
> Если `settings.json` существует, `.env`-значения VK полностью игнорируются.

## 4. Схема базы данных (Supabase / PostgreSQL)

> **⚠️ Supabase free tier:** проект **засыпает** после 1 недели без активности. Первый запрос после пробуждения занимает 3–8 секунд. Это нормально — обрабатывать как медленный cold start, не как ошибку. Лимит хранилища — 500 МБ (для URL-дедупликации хватит надолго).

> **🔒 Row Level Security (RLS):** после создания таблиц обязательно настроить RLS в Supabase. Простейший вариант — запретить всё для `anon` роли и разрешить всё только для `service_role`. Иначе любой, кто знает `SUPABASE_URL` и `SUPABASE_KEY`, сможет читать и писать данные.
> ```sql
> ALTER TABLE used_urls ENABLE ROW LEVEL SECURITY;
> ALTER TABLE scheduled_posts ENABLE ROW LEVEL SECURITY;
> -- политики для service_role создаются автоматически Supabase
> ```
> В `supabase_client.py` использовать `service_role` ключ (из `.env`), а не `anon` ключ.

### 4.1 Таблица `used_urls`

Хранит все URL, которые уже были использованы в постах. Нужна для предупреждения о дублях.
Приведение к нижнему регистру, удаление trailing slash (/ в конце), удаление всех query-параметров, начинающихся на utm_, ref, fbclid

```sql
CREATE TABLE used_urls (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  url          TEXT NOT NULL,
  normalized   TEXT NOT NULL UNIQUE, -- URL без UTM, якоря, трейлинг-слэша
  vk_post_id   BIGINT,               -- ID поста в VK (заполняется после публикации)
  created_at   TIMESTAMPTZ DEFAULT NOW()
);
```

### 4.2 Таблица `scheduled_posts`

Локальный зеркальный учёт постов для быстрой работы календаря и фильтра "без медиа" без постоянных запросов к VK API.

```sql
CREATE TABLE scheduled_posts (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  vk_post_id        BIGINT UNIQUE,
  post_type         TEXT NOT NULL CHECK (post_type IN ('art', 'fursuit', 'video')),
  scheduled_at      TIMESTAMPTZ NOT NULL,
  source_urls       TEXT[] NOT NULL,
  media_attachments JSONB,   -- [{"type": "photo|video", "owner_id": -123, "media_id": 456}]
  post_text         TEXT,
  has_media         BOOLEAN DEFAULT TRUE,
  status            TEXT DEFAULT 'scheduled'
                    CHECK (status IN ('scheduled', 'published', 'error', 'deleted')),
  error_message     TEXT,
  created_at        TIMESTAMPTZ DEFAULT NOW(),
  updated_at        TIMESTAMPTZ DEFAULT NOW()
);
```

## 6. Логика планирования временных слотов

- Пользователь указывает **дату старта** и **часовой пояс** (список IANA timezone names).
- Посты распределяются по слотам последовательно:

```
Слоты: 10:00, 15:00, 20:00
Дата старта: 01.06.2026
Timezone: Europe/Moscow

Пост 1 → 01.06.2026 10:00 MSK
Пост 2 → 01.06.2026 15:00 MSK
Пост 3 → 01.06.2026 20:00 MSK
Пост 4 → 02.06.2026 10:00 MSK
...
```

- **Важно:** перед назначением слота проверить, что он не занят уже существующим отложенным постом в VK. Если занят — пропустить и взять следующий доступный.
- **Кэширование занятых слотов (на бэкенде):**
  1. При вызове `POST /api/preview` бэкенд делает **один** запрос к VK API (`wall.get` с `filter=postponed`) и кэширует занятые слоты в памяти.
  2. Кэш — словарь `{session_key: {slots: set[datetime], expires_at: datetime}}` с TTL = 5 минут.
  3. `session_key` генерируется бэкендом при первом вызове `/api/preview` и возвращается в ответе. Фронтенд передаёт его во всех последующих вызовах `/api/preview` в рамках одной сессии.
  4. Последующие вызовы `/api/preview` используют кэшированные данные вместо повторных запросов к VK API.
  5. **Инвалидация кэша:**
     - Через 5 минут бездействия (TTL).
     - После успешной публикации новых постов (кэш для этого `session_key` очищается).
  6. Это позволяет многократно пересчитывать слоты без лишних запросов к VK.
- Слоты настраиваются в интерфейсе (добавить/удалить/изменить время).

## 7. Пайплайн обработки медиа

### 7.1 Поддерживаемые источники

| Источник            | Метод извлечения                            |
|---------------------|---------------------------------------------|
| YouTube, Bilibili    | yt-dlp (скачать видео)                      |
| Reddit, Twitter/X — фото   | gallery-dl (yt-dlp не распознаёт фото-посты и падает с ошибкой) |
| Reddit, Twitter/X — видео  | yt-dlp                                |
| Прямые ссылки .jpg/.png/.gif/.webp | httpx GET + запись в temp |
| Любой другой сайт   | yt-dlp (попытка); при ошибке → gallery-dl; при ошибке → прямая ссылка |
| Локальные файлы     | multipart/form-data upload                  |

> **Почему gallery-dl, а не только yt-dlp:** yt-dlp ориентирован на видео-контент и не имеет экстракторов для большинства фото-постов Reddit и Twitter/X (галереи, одиночные изображения, альбомы) — попытка извлечь такой URL завершается `ExtractorError` / `UnsupportedError`. `gallery-dl` — специализированный инструмент для скачивания изображений и галерей с этих и других платформ, поддерживает тот же формат `cookies.txt` (Netscape).

### 7.2 Извлечение медиа из URL (backend)

1. Принять URL от frontend.
2. Определить платформу по домену URL.
3. **Извлечение метаданных — порядок попыток:**
   - Сначала запустить `yt-dlp --dump-json <url>` (без скачивания).
     - **Таймаут:** значение `ytdlp_timeout_seconds` из `settings.json` (по умолчанию 30 с). При превышении — ошибка с сообщением «Превышено время ожидания».
     - **Cookies:** если в `./data/cookies.txt` есть файл (загружен через страницу настроек) — передавать `--cookies ./data/cookies.txt`. Если файл отсутствует — попытка без cookies; при ошибке авторизации — предупреждение.
   - **Если yt-dlp вернул ошибку `ExtractorError` / `UnsupportedError`** (характерно для фото-постов Reddit и Twitter/X — yt-dlp не имеет для них экстракторов) — выполнить fallback на `gallery-dl`:
     - Команда: `gallery-dl --dump-json <url>` (без скачивания).
     - Тот же таймаут (`ytdlp_timeout_seconds`) и тот же файл `./data/cookies.txt` (gallery-dl поддерживает Netscape-формат через флаг `--cookies`).
     - Из JSON-вывода gallery-dl сформировать список медиа в том же внутреннем формате, что и для yt-dlp (`type: "photo"`, `thumbnail_url`, `original_url`).
   - Если оба инструмента вернули ошибку — попытаться обработать URL как прямую ссылку на файл (см. §7.1, «Прямые ссылки»).
   - **Зачем файл cookies, а не `--cookies-from-browser`:** файловый подход безопаснее и работает кросс-платформенно; браузерный профиль может быть заблокирован процессом браузера или недоступен при запуске через скрипт.
4. Из метаданных извлечь список медиафайлов (фото / видео) с превью-URL.
5. Вернуть список на frontend для отображения и выбора пользователем.
6. Скачивание фактических файлов происходит только при нажатии «Опубликовать».
   - При скачивании видео через yt-dlp использовать фильтр формата: `-f "bestvideo[height<=1080]+bestaudio/best[height<=1080]"` для ограничения разрешения.
   - При скачивании фото через gallery-dl использовать стандартные настройки (оригинальное качество), без дополнительных фильтров.
   - **Важно:** инструмент для скачивания файла должен совпадать с тем, который успешно вернул метаданные на шаге 3 (т.е. если превью получены через gallery-dl, скачивание тоже выполняется через gallery-dl, а не yt-dlp).
   - **Ограничение размера:** перед загрузкой проверять размер файла — значения `max_photo_size_mb` и `max_video_size_mb` из `settings.json`. Файлы сверх лимита пропускать с ошибкой.

#### Мониторинг здоровья парсеров yt-dlp / gallery-dl

Поскольку `yt-dlp` и `gallery-dl` зависят от внешних платформ, которые могут менять свой HTML/API, парсеры иногда ломаются. Приложение отслеживает ошибки извлечения для каждого домена:

- Счётчик ошибок (`yt_dlp.utils.ExtractorError` / `DownloadError`, а также аналогичные исключения `gallery_dl`) ведётся в памяти для каждого домена (YouTube, Twitter, Reddit и т.д.) за последние 5 минут.
- Если для одного домена накопилось **3 и более ошибок за 5 минут** (суммарно по обоим инструментам) — парсер считается «деградировавшим» (`degraded`).
- При этом:
  - В лог (structlog) записывается предупреждение: `WARNING: Parser for domain 'youtube.com' may be broken, please restart the application`.
  - Эндпоинт `/api/health` начинает возвращать `"ytdlp_health": "degraded"` с деталями.
  - UI при следующем опросе (если используется) может показать toast «Некоторые парсеры устарели. Перезапустите приложение для обновления yt-dlp/gallery-dl».
- Само приложение **не перезапускается автоматически**, чтобы не прерывать текущие задачи публикации.
- При перезапуске приложения (ручном) счётчики сбрасываются, и `pip install --upgrade yt-dlp gallery-dl` в `startup.py` тянет свежие версии.

#### ⚠️ Особый режим для Twitter/X — только последовательная загрузка

Twitter принудительно разрывает соединение (`ConnectionResetError 10054`) при параллельных запросах без авторизации.

**Правило:** если URL принадлежит домену `twitter.com`, `x.com` или `t.co`:
- Всегда использовать **ровно 1 воркер** (`max_workers=1`), независимо от значения `max_download_workers` в настройках.
- Этот лимит жёстко зашит в коде (`media_downloader.py`) и не переопределяется пользователем.
- Рекомендуется также добавить задержку 1–2 секунды между последовательными запросами к Twitter.

Для всех остальных платформ (Reddit, Bilibili, YouTube и т.д.) использовать `max_download_workers` из `settings.json`.

> **Инструкция по получению cookies.txt:** Рекомендуется использовать расширение для браузера **«Get cookies.txt LOCALLY»** (доступно для Chrome и Firefox). Перед экспортом войдите в аккаунт Twitter/X (если требуется) и на любом другом сайте, который требует авторизации. Формат файла — Netscape cookies. Загрузка файла производится через UI на странице настроек (`/settings`).

### 7.3 Загрузка фото в VK

```
1. photos.getWallUploadServer(group_id=GROUP_ID)
   → upload_url

2. POST upload_url с файлом (multipart)
   → {server, photo, hash}

3. photos.saveWallPhoto(group_id, server, photo, hash)
   → attachment = "photo{owner_id}_{id}"

4. Удалить временный файл
```

### 7.4 Загрузка видео в VK

```
1. video.save(group_id=GROUP_ID, name="...", wallpost=0)
   → {upload_url, video_id, owner_id}

2. POST upload_url с файлом (multipart)
   → подтверждение

3. attachment = "video{owner_id}_{video_id}"

4. Удалить временный файл
```

### 7.5 Ограничение: 10 медиафайлов на пост

Если суммарно медиа > 10 в одном посте:
- На шаге предпросмотра показать все медиа с чекбоксами.
- Предварительно выбрать первые 10.
- Пользователь может вручную изменить выбор (но не более 10).
- Отображать счётчик `Выбрано: N / 10`.

### 7.6 Временные файлы

- Хранятся в `<tempdir>/vk_scheduler/<task_id>/`, где `<tempdir>` — результат `tempfile.gettempdir()` (на Windows это `%TEMP%`, на Linux/macOS — `/tmp`). Путь вычисляется в Python при старте: `Path(tempfile.gettempdir()) / "vk_scheduler"`.
- Удаляются сразу после успешной загрузки каждого файла в VK.
- При старте приложения — очистка папок старше 24 часов.
- **Ограничение суммарного размера:** если общий размер `<tempdir>/vk_scheduler/` превышает `MAX_TEMP_SIZE_GB` (из `.env`, по умолчанию 3 ГБ), удалять самые старые папки до тех пор, пока размер не станет ниже лимита.
- **Потоковая запись на диск:**
  - Для прямых HTTP-ссылок (jpg, png, gif, webp, mp4 по прямой ссылке) используется `httpx.stream()` с записью чанками напрямую в файл, без полной загрузки в оперативную память (аналог `io.Copy`).
  - Для `yt-dlp` потоковый режим невозможен архитектурно: библиотека всегда сохраняет готовый файл во временную директорию, так как для YouTube и Bilibili требуется склейка видео- и аудиопотоков через ffmpeg. Это не является утечкой памяти, а лишь временным использованием диска.
- **Немедленное удаление:** после успешной загрузки каждого медиафайла в VK (через `photos.saveWallPhoto` или `video.save`) исходный временный файл удаляется через `unlink()`, даже если папка задачи ещё существует.

### 7.7 Ограничение параллельных задач

- Максимальное количество одновременно выполняющихся фоновых задач публикации — `MAX_CONCURRENT_TASKS` (из `.env`, по умолчанию 3). Это системный лимит приложения, не путать с `max_download_workers` из `settings.json`.
- `max_download_workers` из `settings.json` — количество параллельных потоков при скачивании медиа внутри одной задачи (применяется ко всем платформам кроме Twitter, см. §7.2).
- Реализация: `asyncio.Semaphore` в task_store. Задачи сверх лимита ставятся в очередь.
- Статус задачи при этом остаётся `pending`.
- Это предотвращает одновременную загрузку десятков видео, которая может исчерпать диск и память.

### 7.8 Оптимизация памяти и диска

- **Прямые HTTP-ссылки (httpx):** использовать потоковую загрузку (`stream=True`) — файл пишется на диск чанками без полной буферизации в RAM.
- **yt-dlp / gallery-dl:** потоковый режим **невозможен** — оба инструмента всегда сохраняют файл во временную директорию перед отправкой. Для yt-dlp это связано с необходимостью сшивки видео- и аудио-потоков через `ffmpeg` (YouTube, Bilibili); для gallery-dl — со стандартной архитектурой загрузчика. Это архитектурное ограничение, не баг.
- Итог: все файлы проходят через `<tempdir>/vk_scheduler/<task_id>/` и удаляются после успешной загрузки в VK.

## 8. Backend API (FastAPI)

Базовый префикс: `/api`
Версия VK API: `5.199`

### 8.3 `POST /api/publish`

Скачать медиа, загрузить в VK, создать отложенные посты. Возвращает результаты по каждому посту.

**Request:**
```json
{
  "posts": [/* массив из /api/preview, возможно отредактированный пользователем */]
}
```

**Response (мгновенный):**
```json
{
  "task_id": "uuid"
}
```

После вызова `/api/publish`:
- **Предварительная валидация (до создания задачи):** проверить что все `scheduled_at` в запросе строго больше текущего времени И не дальше 1 года вперёд (ограничение VK API). Если хотя бы один пост нарушает условие — вернуть `400 Bad Request` с описанием конкретных нарушений, задачу не создавать.
- Backend создаёт задачу в in-memory хранилище (словарь `task_id → TaskStatus`) и запускает фоновую обработку через `asyncio.create_task`.
- **Задержка между публикациями:** после каждого успешного вызова `wall.post` делать `await asyncio.sleep(vk_publish_delay_seconds)` (значение из `settings.json`, по умолчанию 5 секунд). Это предотвращает ошибку Too Many Requests со стороны VK API при пакетной публикации.
- Фронтенд опрашивает статус через `GET /api/task/{task_id}` с интервалом 2-3 секунды.
- Все использованные URL записываются в таблицу `used_urls`.
- Каждый пост записывается в таблицу `scheduled_posts`.

### 8.3b `GET /api/task/{task_id}`

Получить статус выполнения задачи публикации (polling).

**Response:**
```json
{
  "task_id": "uuid",
  "status": "processing",
  "started_at": "2026-06-10T10:00:05+03:00",
  "finished_at": null,
  "progress": {
    "current": 2,
    "total": 5,
    "stage": "uploading_media"
  },
  "results": [
    {
      "post_id": "uuid",
      "vk_post_id": 12345,
      "status": "ok"
    },
    {
      "post_id": "uuid",
      "vk_post_id": null,
      "status": "error",
      "error": "Media download failed: HTTP 403"
    }
  ]
}
```

**Поля статуса:**
| status | Описание |
|--------|----------|
| `pending` | Задача создана, ожидает начала обработки |
| `processing` | Идёт скачивание медиа и публикация |
| `completed` | Все посты обработаны (успешно или с ошибками) |
| `error` | Критическая ошибка задачи (все ретраи исчерпаны) |
| `cancelled` | Задача отменена пользователем до начала обработки |

**Этапы (`stage`):**
| stage | Описание |
|-------|----------|
| `downloading_media` | Скачивание медиафайлов через yt-dlp / httpx |
| `uploading_media` | Загрузка медиа в VK (фото/видео) |
| `creating_posts` | Создание отложенных постов через wall.post |
| `done` | Задача завершена |

**Примечания по реализации:**
- Хранилище задач — in-memory (словарь Python). При перезапуске backend'а статусы теряются — это приемлемо для локального приложения.
- Старые task_id (старше 1 часа) удаляются фоновой задачей каждые 15 минут для предотвращения утечки памяти.
- `started_at` и `finished_at` — ISO8601 с timezone. `started_at` заполняется при переходе `pending → processing`, `finished_at` — при переходе в `completed` или `error`.
- **Отмена задачи:** `DELETE /api/task/{task_id}` — прерывает выполнение задачи, если она ещё в статусе `pending`. Для уже выполняющихся задач (`processing`) возвращает `409 Conflict`. При успешной отмене задача переводится в статус `cancelled`.

### 8.4 Управление отложенными постами

| Метод | Путь | Описание |
|-------|------|----------|
| GET | `/api/scheduled` | Получить все отложенные посты из VK API + синхронизировать с БД |
| GET | `/api/scheduled/calendar?year=2026&month=6` | Агрегация: количество постов по датам |
| GET | `/api/scheduled/no-media` | Посты без прикреплённых медиафайлов |
| GET | `/api/scheduled/{vk_post_id}` | Детали поста |
| PUT | `/api/scheduled/{vk_post_id}` | Изменить дату/время, текст поста (wall.edit) |
| DELETE | `/api/scheduled/{vk_post_id}` | Удалить пост (wall.delete) |
| GET | `/api/task/{task_id}` | Статус задачи публикации (polling, см. 8.3b) |
| DELETE | `/api/task/{task_id}` | Отменить задачу публикации (если ещё pending, см. 8.3c) |

**Логика синхронизации в `GET /api/scheduled`:**
1. Получить актуальный список постов из VK API (`wall.get`, filter=postponed, все страницы).
2. Посты из VK, которых нет в `scheduled_posts` → `INSERT` (могли быть созданы вручную в VK).
3. Записи в `scheduled_posts` со статусом `scheduled`, которых больше нет в VK → обновить статус на `deleted` (пост удалили напрямую в VK, не через приложение).
4. Вернуть актуальный список клиенту.

**PUT Request body:**
```json
{
  "scheduled_at": "2026-06-15T15:00:00+03:00",
  "post_text": "...",
  "media_items": [...]               // опционально — только если нужно изменить медиа
}
```

**⚠️ Ограничение VK API:** `wall.edit` **не позволяет** изменять attachments у существующего отложенного поста. Если в запросе передан непустой `media_items` и он отличается от текущих медиа поста:
1. Создать новый отложенный пост (`wall.post`) с новыми медиа, тем же текстом и тем же `publish_date`.
2. Удалить старый пост (`wall.delete`).
3. Обновить запись в `scheduled_posts` (новый `vk_post_id`).

**Важно — гонка за слот:** между удалением старого и созданием нового поста слот могут занять. Поэтому:
- Сначала создать новый пост (слот занимается).
- Затем удалить старый (слот освобождается, но уже занят новым).
- Если создание упало — старый пост НЕ удалять, вернуть ошибку.

### 8.6 `GET /api/settings` / `PUT /api/settings`

Получить и сохранить пользовательские настройки. Читает/пишет `settings.json`.

**GET Response:**
```json
{
  "vk_token_configured": true,
  "vk_token_hint": "vk1.a.Ab...",
  "vk_group_id": 123456,
  "vk_owner_id": 654321,
  "time_slots": ["10:00", "15:00", "20:00"],
  "timezone": "Europe/Moscow",
  "max_download_workers": 3,
  "vk_publish_delay_seconds": 5,
  "ytdlp_timeout_seconds": 30,
  "max_photo_size_mb": 50,
  "max_video_size_mb": 500,
  "cookies_uploaded_at": "2026-06-10T10:00:00+03:00"
}
```

> **Полный токен НИКОГДА не возвращается в GET-ответе.** `vk_token_hint` — только первые 8 символов для отображения в UI. Это предотвращает перехват токена через DevTools / расширения браузера.

**PUT Request body:**
```json
{
  "vk_token": "vk1.a...",
  "vk_group_id": 123456,
  "vk_owner_id": 654321,
  "time_slots": ["10:00", "15:00", "20:00"],
  "timezone": "Europe/Moscow",
  "max_download_workers": 3,
  "vk_publish_delay_seconds": 5,
  "ytdlp_timeout_seconds": 30,
  "max_photo_size_mb": 50,
  "max_video_size_mb": 500
}
```

> Если поле `vk_token` в PUT-запросе пустое (`""` или отсутствует) — существующий токен в `settings.json` **не перезаписывается**. Это позволяет обновить другие настройки не вводя токен заново.

**Валидация на бэкенде перед сохранением:**
- `time_slots`: непустой массив, каждый элемент соответствует `HH:MM`, отсортирован по возрастанию.
- `timezone`: валидный IANA timezone (проверить через `pytz.timezone(value)`).
- `max_download_workers`: целое число 1–10.
- `vk_publish_delay_seconds`: целое число 1–60.
- `ytdlp_timeout_seconds`: целое число 5–300.
- `max_photo_size_mb`: 1–50 (лимит VK API).
- `max_video_size_mb`: 1–2048.

> `cookies_uploaded_at` — только для чтения, устанавливается сервером. В PUT-запросе игнорируется.

## 9. VK API — используемые методы

Все запросы: `https://api.vk.com/method/<method>?access_token=VK_TOKEN&v=5.199`

| Метод VK API              | Назначение                                      |
|---------------------------|-------------------------------------------------|
| `wall.get`                | Список отложенных постов (`filter=postponed`)   |
| `wall.post`               | Создать отложенный пост                         |
| `wall.edit`               | Редактировать пост                              |
| `wall.delete`             | Удалить пост                                    |
| `photos.getWallUploadServer` | Получить URL для загрузки фото              |
| `photos.saveWallPhoto`    | Сохранить фото после загрузки                   |
| `video.save`              | Инициализировать загрузку видео                 |
| `users.get`               | Имя и аватар текущего аккаунта                  |
| `groups.getById`          | Имя и аватар группы                             |
| `utils.getShortLink`      | Сократить URL через vk.cc                       |

**Параметры `wall.post`:**
```json
{
  "owner_id": "-{GROUP_ID}",
  "from_group": 1,
  "message": "✯ #art@xkemonox ✯\n\nSource: https://vk.cc/abc",
  "attachments": "photo-{GROUP_ID}_{PHOTO_ID},video-{GROUP_ID}_{VIDEO_ID}",
  "publish_date": 1749600000
}
```

**⚠️ Пагинация `wall.get`:** VK API возвращает максимум 100 постов за один запрос. При лимите в 150 отложенных постов необходимо:
- Собирать все посты циклом: запрашивать `offset=0, count=100`, затем `offset=100, count=100` и т.д., пока не вернётся меньше, чем `count`.
- Endpoint'ы `GET /api/scheduled` и `GET /api/scheduled/calendar` должны агрегировать результаты всех страниц.

**⚠️ Ограничение `publish_date`:** значение должно быть строго больше текущего времени и не превышать **1 год** от текущей даты. Нарушение вернёт ошибку VK API. Валидация выполняется на бэкенде в `POST /api/publish` до создания задачи (см. §8.3).

### 10.3 Страница создания постов `/create/:type`

Трёхшаговый интерфейс (Steps / Wizard).

#### Шаг 1 — Источники

- Поле ввода URL (textarea, одна ссылка на строку) + кнопка **«Добавить»**
- Кнопка **«Загрузить файлы»** (drag & drop зона, форматы: jpg, png, gif, webp, mp4, mov)
  - **Превью локальных файлов:** после выбора файлов через `<input type="file">` или drag & drop, немедленно показать миниатюры через `URL.createObjectURL()` на фронтенде. Файлы при этом НЕ загружаются на сервер — они будут отправлены только на этапе публикации.
  - Для видеофайлов: показать иконку видео + имя файла. Извлечение первого кадра через `<video>` + canvas зависит от поддержки кодеков браузером и может не работать для HEVC/AV1 — реализовать как опциональную фичу, только если файл воспроизводится в `<video>`.
- После добавления каждого источника — карточка с:
  - URL источника
  - Превью всех найденных медиафайлов (миниатюры)
  - Чекбокс у каждого медиафайла (по умолчанию все выбраны)
  - Красный бейдж **«Уже использовано»** если URL есть в `used_urls`
  - Кнопка удалить источник
- Кнопка **«Объединить выбранные в один пост»** — группирует несколько источников под одним постом
- Если суммарно выбрано > 10 медиа в одном посте: жёлтое предупреждение + автоснятие лишних чекбоксов

#### Шаг 2 — Настройки планирования

- **Дата начала** (date picker, по умолчанию: завтра)
- **Часовой пояс** (select, список IANA, по умолчанию из `settings.json`)
- **Временные слоты** (список с возможностью добавить / удалить / изменить время; по умолчанию из `settings.json`)
- Кнопка **«Предпросмотр»**

#### Шаг 3 — Предпросмотр и редактирование

Список карточек постов. Каждая карточка содержит:

- Дата и время (редактируемое, datetime-picker)
- Миниатюры медиа с кнопкой ✕ у каждой
- Кнопка **«+ Добавить медиа»** (из уже загруженных или новый URL)
- Текст поста (редактируемое textarea)
- Кнопка переместить карточку вверх/вниз

Внизу страницы:
- Кнопка **«Опубликовать всё»**
- Прогресс-бар с текущим статусом (`Загрузка медиа 2/5... Публикация поста 1/5...`)
- После завершения: сводка (`Опубликовано: 5, Ошибок: 0`)

### 10.4 Страница «Все посты» `/posts/calendar`

#### Выбор периода

- Выпадающий список **год** (текущий год ± 2 года)
- Сетка или список **месяцев**

#### Сетка месяца

Таблица 7 колонок (Пн–Вс) × N строк:

- Каждая ячейка: число + бейджи с количеством по типам
  - `art: 2` (синий)
  - `fursuit: 1` (зелёный)
  - `video: 3` (красный)
- Ячейки с итого >= 3 постами — выделены цветом фона
- Клик по ячейке → раскрывается боковая панель или модальное окно

#### Детали дня (при выборе даты)

Список постов, отсортированных по времени. Каждый пост:
- Время публикации

## 11. Обработка ошибок и Edge Cases

### 11.1 Ретраи (повторные попытки)

Для критичных сетевых операций использовать экспоненциальный backoff:

| Операция | Попыток | Интервалы | Ситуации для ретрая |
|----------|---------|-----------|---------------------|
| Загрузка медиа в VK | 3 | 1с, 4с, 16с | HTTP 429, 5xx, таймаут |
| `wall.post` | 3 | 1с, 4с, 16с | HTTP 429, 5xx |
| yt-dlp `--dump-json` | 2 | 2с, 8с | `RequestError`, HTTP 429, 5xx |
| Прямая загрузка (httpx) | 2 | 2с, 8с | HTTP 429, 5xx, таймаут |

Если все попытки исчерпаны — пост помечается `error` (для публикации) или возвращается ошибка в карточке (для `/extract`).

### 11.2 Edge Cases

| Ситуация | Поведение |
|----------|-----------|
| URL уже использован | Предупреждение в UI (бейдж), пользователь может продолжить |
| yt-dlp не поддерживает сайт | Попытка прямой загрузки; если неудача — ошибка в карточке |
| Медиа недоступно (403, 404) | Ошибка в карточке, остальные посты не блокируются |
| Ошибка загрузки в VK | Пост записывается в БД со статусом `error`, появляется в `/posts/no-media` |
| > 150 отложенных постов в VK | Предупреждение в шапке (лимит VK на отложенные посты) |
| Таймаут yt-dlp | Ошибка в карточке: «Превышено время ожидания при извлечении медиа» |
| Таймаут загрузки файла в VK | 5 минут; показать ошибку и пропустить |
| Нет соединения с VK API | Toast-уведомление с деталями ошибки |
| Twitter `ConnectionResetError(10054)` | Уже предотвращено архитектурно (принудительно 1 поток для Twitter). Если всё равно произошло — retry с задержкой 3 с, затем ошибка в карточке |
| Twitter/X заблокировал запрос (401/403) | Предупреждение: «Требуются cookies. Загрузите cookies.txt на странице настроек» |
| VK API ошибка 429 (Too Many Requests) при публикации | Уже предотвращено задержкой `vk_publish_delay_seconds`. Если всё равно произошло — экспоненциальный retry (см. §11.1) |
| Файл превышает лимит размера | Ошибка: «Файл превышает максимальный размер (X МБ)», пост пропускается |
| Превышен лимит параллельных задач | Задача ставится в очередь со статусом `pending` |
| Превышен суммарный размер /tmp | Фоновая очистка: удаление самых старых папок до освобождения места |
| Неверный VK токен при старте | Шапка показывает «⚠️ Ошибка подключения к VK» с ссылкой на `/settings` |
| Повторяющиеся ошибки парсера для одного домена (≥3 за 5 минут) | Парсер помечается как `degraded`; `/api/health` возвращает предупреждение; UI (при наличии) показывает уведомление о необходимости перезапуска приложения |

### 11.3 Логирование

- **Библиотека:** `structlog` — структурированное JSON-логирование.
- **Уровень логирования:** настраивается через `LOG_LEVEL` в `.env` (по умолчанию `INFO`).
- **Формат:** каждая строка — JSON-объект с полями `timestamp`, `level`, `event`, `logger`, `extra` (контекст запроса/ошибки).
- **Вывод:** stdout. Опционально — дублирование в файл `backend/logs/app.log` через `logging.FileHandler` (полезно при запуске в фоне через `start.bat`).
- **Контекст на запрос:** middleware FastAPI добавляет `request_id` (UUID) и `url` в каждую запись лога в рамках обработки одного HTTP-запроса.

**Ключевые точки логирования:**

| Событие | Уровень | Контекст |
|---------|---------|----------|
| Запрос к VK API | DEBUG | метод, параметры, время ответа |
| Ошибка VK API | ERROR | метод, код ошибки, сообщение |
| Запуск yt-dlp | INFO | URL, PID процесса |
| Ошибка yt-dlp | ERROR | URL, stderr, exit code |
| Успешная публикация | INFO | vk_post_id, post_type, source_urls |
| Загрузка медиа в VK | INFO | тип (photo/video), размер файла, время загрузки |
| Старт/остановка приложения | INFO | версия, конфигурация |
| Обнаружено падение парсера (деградация) | WARNING | domain, error_count, период |
| Сброс счётчика ошибок при перезапуске | INFO | domain, предыдущий статус |

### npm-скрипты (корневой `package.json`)

```json
{
  "scripts": {
    "setup": "pip install -r backend/requirements.txt && npm install --prefix frontend",
    "start": "concurrently --names \"backend,frontend\" --prefix-colors \"cyan,magenta\" \"python backend/startup.py\" \"npm run dev --prefix frontend\"",
```

> `concurrently` запускает оба процесса в одном терминале с цветными метками `[backend]` и `[frontend]`. Ctrl+C завершает оба.

---

### `backend/startup.py` — точка входа backend'а

Заменяет `entrypoint.sh` из Docker-версии. Выполняется перед запуском uvicorn.

```python
import subprocess
import sys
import uvicorn

def upgrade_extractors():
    print(">>> Upgrading yt-dlp and gallery-dl to latest versions...")
    subprocess.run(
        [sys.executable, "-m", "pip", "install", "--upgrade", "--quiet", "yt-dlp", "gallery-dl"],
        check=True
    )

if __name__ == "__main__":
    upgrade_extractors()
    print(">>> Starting FastAPI server...")
    uvicorn.run("main:app", host="127.0.0.1", port=8000, reload=False)
```

> **Важно:** backend слушает только `127.0.0.1:8000` (не `0.0.0.0`) — не доступен из сети, только с локальной машины.

### Рекомендации для длительной работы

Приложение рассчитано на ручной запуск и перезапуск (например, раз в 1-2 дня для обновления `yt-dlp`). Если требуется непрерывная работа в течение нескольких недель, рекомендуется использовать менеджер процессов, который автоматически перезапускает процессы при падении:

- **Windows:** `pm2` (через WSL), `nssm` (сервис Windows).
- **Linux:** `systemd` (создать юнит), `pm2` или `supervisor`.
- **macOS:** `launchd` или `pm2`.

Пример для `pm2`:
```bash
npm install -g pm2
pm2 start "npm start" --name vk-scheduler
pm2 save
pm2 startup
```

При этом каждый перезапуск бэкенда будет выполнять `pip install --upgrade yt-dlp gallery-dl`, что решает проблему устаревших парсеров.

**Про `static-ffmpeg`:**

Пакет `static-ffmpeg` при первой загрузке скачивает статически слинкованный бинарник `ffmpeg` для текущей платформы (Windows / Linux / macOS) и сохраняет его в папку пакета. Для интеграции с yt-dlp нужно один раз при старте прописать путь:

```python
# в startup.py или config.py
import static_ffmpeg
static_ffmpeg.add_paths()   # добавляет ffmpeg в PATH текущего процесса
```

После этого yt-dlp найдёт ffmpeg автоматически. Пользователю **не нужно** ничего устанавливать вручную.

> **Почему не системный ffmpeg?** Он может отсутствовать или быть устаревшим. `static-ffmpeg` гарантирует актуальную версию на любой машине без прав администратора.
